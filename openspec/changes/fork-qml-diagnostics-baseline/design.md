# Design

## The baseline is a generated registry that auto-merges wrong

`qml-diagnostics-baseline.json` is generated by `scripts/qmllint_report.py
--update-baseline` and carries a `_README` saying "Do not hand-edit." On upstream
it is regenerated whenever the QML tree changes and committed. When the fork syncs,
git merges that file textually — and because upstream only ever adds/removes its own
files and clears its own residue, the merged result is **upstream's** view: a
`clean` list of upstream's 219 files and `ceilings: {}`.

This is the same failure mode already documented for other generated registries in
this fork — migration chains, `qmlRegister` blocks, the `LayoutItemDelegate` switch,
the widget catalog: **a textually-clean auto-merge of an append-only/generated
registry is not semantically clean.** The fix is the same in spirit: the fork owns
its copy and regenerates it after a sync, rather than accepting upstream's.

The alternative — teaching the merge to union the two baselines — is rejected. The
baseline is not a hand-authored union of independent entries; it is a snapshot of
what the tool reports on one tree. A unioned baseline would assert counts for files
as they exist on neither tree. Regeneration on the fork tree is the only source of
truth.

## Under-resolution is the trap; certify the run before trusting counts

The gate script's own docstring records `#1680`: a baseline regenerated from a build
where types were **under-resolving** wrote too-low ceilings, and "fails silently in
the safe-looking direction." The inverse bites here too — an under-resolving run
*inflates* `unqualified` (every reference to an unresolved type reads as unqualified)
and *raises* `unresolved-type`. The 4 `unresolved-type` occurrences and some of the
"had none" unqualified counts are plausibly this, not genuine debt.

Consequence for sequencing: **do task 1 (register the fork QML) and a clean
`Decenza.qmltypes` build before measuring anything.** Counts taken before types
resolve will send task 2 chasing phantom accesses. The script has a staleness guard
that refuses `--update-baseline` on a run it judges stale; honour it, never
`--allow-stale`. CLAUDE.md's note applies directly — "a qmllint count going UP after
a fix is usually the fix working," because resolving a type lets the linter reach
expressions it previously abandoned.

## Why not just re-baseline and move on

Because the `qml-diagnostics` capability forbids it for the category that matters.
`unqualified` is never exemptible and new files must reach zero; a baseline that
simply records the barista components' current unqualified counts as ceilings would
launder genuine undeclared-identifier bugs — the exact 2.0.1 `#1661` defect — into
"accepted backlog." So the order is: resolve first, record only the delegate-scope
residue (`ComponentBehavior: Bound` kind), then regenerate. Re-baselining is the
last step, not the fix.

## Scope boundary with the C++ side

The C++ objects most of these accesses resolve against (`BaristaStorage`,
`LiveShotCoach`, and the barista singletons) are already registered correctly —
`FINAL` `Q_PROPERTY` on `maincontroller.h`, verified during the 2026-08-01 sync. So
the resolution work is expected to be QML-side (module registration of the QML
components themselves, imports) rather than a C++ `setContextProperty` migration,
which upstream already completed. If any fork object turns out to be context-injected,
that is a genuine `qml-diagnostics` violation to migrate, not to baseline.
